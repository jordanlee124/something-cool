# Porting Ember Vale to Unity

## Where things stand

`ember-vale.html` is about 5,300 lines. Roughly 3,350 of them are simulation (world, steward AI, economy, diplomacy,
war, trade, history), about 850 are the canvas renderer and about 350 are the HTML UI. The HTML game is still gaining
features, so this port is chasing a moving target.

## Decisions

1. **Sim and view are separate assemblies.** `EmberVale.Sim` has `noEngineReferences`, so it cannot touch UnityEngine.
   It compiles under plain `dotnet`, which is how it is tested here, and it can be run headless for balance checks.
2. **3D low-poly look, grid logic.** The sim stays a tile grid (1 tile = 1 unit). The view is a fixed, tilted perspective
   camera over 3D Blender models. Cost: more art to make per building and per era than the 2D canvas needs.
   Alternative if art becomes the bottleneck: a 2D sprite look with the same sim.
3. **Seeded randomness.** The HTML uses `Math.random`. The port uses a seeded `Rng` so runs can be replayed and tested.
   Consequence: the two versions cannot produce the same village layout from the same seed, only the same terrain.
4. **Blender assets are generated by script**, not hand-modelled, so the whole set can be rebuilt, restyled and
   re-exported in one command (`blender/generate_assets.py`). Flat palette materials, one per colour, tinted per
   faction in Unity with a `MaterialPropertyBlock`.
5. **iOS target:** URP, IL2CPP, ARM64, iOS 15+, portrait, no HDR, no post-processing, SRP batcher.

## Keeping the two versions from diverging

The honest problem: every feature added to the HTML after this point is a feature the port does not have.

- The HTML game is the design source of truth. A feature is not ported until it has stopped changing.
- Port by vertical slice in the order the game plays: map and settlers (done), jobs and buildings, steward and
  growth, economy, politics, war. Each slice gets a row in the table below.
- Cross-checks tie the two together. `Tools~/parity/terrain.js` runs the HTML's own generator, and `SimCheck` fails if
  the C# differs. Add a parity check whenever a ported piece is deterministic.
- Option to decide on later: freeze HTML features at a version (say v34) and port that, then resume features in Unity only.

## Port ledger

| Slice | HTML | Unity |
| --- | --- | --- |
| Terrain generation | `World.generate` | done, identical on 4 seeds |

## Rough cost (Guessing)

The sim is the bulk. Expect about 5,000 to 6,000 lines of C# for the sim, 1,500 for the view, and a UI Toolkit
front end. The ledger above has ten rows; the first took one session and the later ones (economy, war) are each
several times bigger. Plan on many sessions, not one.

## What cannot be done from the cloud container

No Unity editor and no Xcode here. The Unity scripts have not been compiled by Unity, the URP setup call is untested,
and nothing has run on an iPhone. The first thing to do on a machine with Unity is open the project and fix whatever the
console reports; expect a small number of API-name errors.

## Performance notes

The HTML game holds 60 fps on an iPhone at about 780 people. Unity will not be the bottleneck for the sim; draw calls
will be. The demo scene instantiates one GameObject per tree, which is fine for 3,000 tiles and not fine for a grown map.
Next step for the view is chunked static meshes or `Graphics.RenderMeshInstanced`.
